# SUN AID 予約管理・入金確認・予約カレンダー

## 何が起きるか

1. お客様は今までどおり予約リクエストフォームを送ります。有効な未確定申込みは公開カレンダーで「□ 商談中」として表示します。既存の管理者宛メール通知は別の仕組みなので、稼働中の処理を確認して維持します。
2. 貸出条件と請求額を確認し、条件付きならお客様の了承を記録します。管理画面から振込案内を送るか、自動案内を有効にした場合は処理対象にします。送信だけでは予約確定になりません。
3. 管理者が「カレンダーとの重複を確認」で、請求確認額・貸出条件・競合予定・先行商談を確認します。銀行入金を別途確認し、「最終承認して予約確定」を押します。承認時に重複と申込の変更を再検査します。
4. Apps ScriptがGoogleカレンダー「予約」に、レンタルする方の名前と申込内容を含む非公開イベントを作成します。
5. HPの予約ページは同じカレンダーから利用日時だけを読み込み、重なる時間を選べないようにします。名前・メールアドレス・イベント名・説明は公開APIから返しません。

同じ予約確定操作を再度行ってもイベントは重複しません。カレンダーの予定または重なる先行商談があれば、振込案内と確定を止めます。競合や入金後の条件変更は管理者が個別対応します。

通常案件の完全自動判定・請求額の自動検証は未接続です。現時点の自動案内エンジンは、管理者が確認・保存した条件と請求額だけを使います。フォームの自由記載の概算額をそのまま自動請求しません。A2の検証済み金額との接続は別作業です。

## アカウントとデータ

- 管理者アカウントは `sunaid20220708@gmail.com` と `info@izutrip.com`。
- 元の回答タブは読み取り専用。記録先は同じスプレッドシート内の `SUN_AID_送信履歴`、`SUN_AID_予約確定履歴`、`SUN_AID_予約対応`。
- カレンダーイベントには名前、メール、利用日時、申込内容を保存し、Googleカレンダー上で「非公開」にします。カレンダー「予約」は管理担当者だけが見られるよう共有設定を確認してください。
- HPの公開用APIは予約日時の開始・終了のみ返します。予約ページは日時の取得に失敗した場合、予約リクエストへの進行を止めます。
- □は未確定です。重なる後続申込みも受け付けますが、先行案件が未確定の間は後続への振込案内を止めます。□は申込一覧から算出し、Googleカレンダーへ仮予約イベントを追加しません。
- 商談期限と自動失効は未決定です。この版は自動失効させず、管理画面の「商談を終了して□を解除」で終了を記録します。案内済み・入金済みの案件を終了する場合は顧客対応を先に確認します。
- ○△□×は日単位の目安です。表示の優先順位は×→□→△→○。時間の選択と最終確認は時間帯で判定します。

## 1. フォームのメールアドレス

回答シートの見出しに `メールアドレス` 列があり、過去のテスト回答にも値が入ることを確認します。フォームの設定表示はアカウントやフォームの種類によって異なります。スクリプトは回答シートの実際の列見出しを `EMAIL_HEADER` で使います。メールがない、または不正な申込は送信できません。

## 2. Googleカレンダーを準備

1. `sunaid20220708@gmail.com` でGoogleカレンダーを開き、既存のカレンダー「予約」を確認します。まだなければ「予約」という名前で作成します。
2. そのカレンダーの設定で「カレンダーの統合」からカレンダーIDをコピーします。`sunaid20220708@gmail.com` 自身の「予約」カレンダーならIDはメール形式の場合があります。IDはコードやチャットへ貼らず、Apps Scriptのスクリプトプロパティにだけ保存します。
3. Apps Scriptを実行するアカウントが `info@izutrip.com` の場合、「予約」カレンダーをその実行アカウントへ共有し、「予定の変更」権限を付けます。info@がエイリアスの場合は、実際にスクリプトを所有・実行するGoogleアカウントへ共有します。
4. カレンダーの共有範囲を一般公開にしないでください。イベントはスクリプトから非公開に設定します。

## 3. Apps Scriptを設定

1. 稼働中のフォーム・回答シート・Apps Script全文とトリガー・カレンダー・Vercel設定の対応を確認します。接続先を特定する前に、稼働中の `Code.gs` を置き換えないでください。既存の受付メール処理との依存・関数名衝突を確認します。
2. まず独立した検証用シート・カレンダー・Apps Scriptで、`apps-script/Code.gs` を配置します。本番への適用は検証と既存処理の照合後に行います。
3. プロジェクト設定で「appsscript.json マニフェスト ファイルをエディタで表示」を有効にし、`apps-script/appsscript.json` 全体を貼り替えます。カレンダー権限を含むため、再承認が必要です。
4. プロジェクト設定 → スクリプト プロパティへ以下を登録します。

| 名前 | 値 |
|---|---|
| `SPREADSHEET_ID` | 回答スプレッドシートURLの `/d/` と `/edit` の間 |
| `RESPONSE_SHEET_ID` | 回答タブのgid。確認済みの値：`405558677` |
| `EMAIL_HEADER` | 回答シートのメール列見出し。通常は `メールアドレス` |
| `RESERVATION_CALENDAR_ID` | 2章でコピーした「予約」カレンダーID |
| `BACKEND_SECRET` | 32文字以上の乱数。Vercelの `ADMIN_BACKEND_SECRET` と同じ値 |
| `ENABLE_CUSTOMER_SEND` | 初期値 `false` |
| `ENABLE_AUTO_GUIDANCE` | 初期値 `false`。確認済み案件の自動案内を有効にする場合のみ `true` |

秘密値やカレンダーIDをチャット、コード、GitHubへ貼らないでください。

5. 検証用プロジェクトで関数一覧から `setup` を選び、実行して権限を許可します。上記3つの履歴・対応タブが作成されることを確認します。既存の送信・確定履歴は上書きしません。メールは送信されません。
6. デプロイ → 新しいデプロイ → 種類「ウェブアプリ」。実行ユーザーは自分、アクセスできるユーザーは「全員」にします。表示された `/exec` URL を控えます。URLだけではデータを読めず、Vercelの署名が必要です。
7. ウェブアプリを変更したときは、デプロイの管理から新しいバージョンへ更新します。`/dev` のテストURLは使いません。

## 4. Googleログイン

Google CloudのOAuthウェブクライアントを使います。Googleログインの承認済みJavaScript生成元には管理画面Previewのオリジンだけを登録し、`/admin/` などパスは入れません。テストユーザーを求められたら上記2アカウントを登録し、クライアントIDを控えます。クライアントシークレットは使いません。

## 5. Vercel Preview

Vercelプロジェクトの Settings → Environment Variables で、まず対象ブランチのPreviewに設定します。

| 名前 | 値 |
|---|---|
| `ADMIN_GOOGLE_CLIENT_ID` | 4章のOAuthクライアントID |
| `ADMIN_ORIGIN` | Preview管理画面URLのオリジン（`https://` とホスト名だけ） |
| `ADMIN_SESSION_SECRET` | 32文字以上の乱数 |
| `ADMIN_BACKEND_URL` | Apps Scriptウェブアプリの `/exec` URL |
| `ADMIN_BACKEND_SECRET` | Apps Script `BACKEND_SECRET` と完全に同じ値 |

`ADMIN_SESSION_SECRET` と `ADMIN_BACKEND_SECRET` は別々の乱数にします。保存後、Previewを再デプロイします。予約ページと管理APIは同じVercelデプロイに配置します。カレンダーにアクセスできない場合、公開空き状況APIはエラーになり、予約ページは申込フォームへ進ませません。

## 6. 検証

1. Previewの予約ページを開き、予約済み時間のある日が表示されること、日時が重なれば選べないことを確認します。
2. `/api/availability` の `bookings`、`inquiries`、`pending` の各要素に `start` と `end` だけが含まれ、名前・メール・イベント説明・予約ID・イベントIDがないことを確認します。GASとVercelの版が不一致なら申込みを停止することも確認します。
3. 架空の予約申込みを回答シートへ入れ、管理画面で表示を確認します。実在顧客を使わないでください。
4. 予約申込みの振込案内メールを自分宛に送って受信を確認します。案内メール送信だけで予約確定にならないことを確認します。
5. 貸出条件と請求額を保存し、重複確認結果を表示してから、架空申込みの入金確認・最終承認を実行します。カレンダーに非公開イベントが一度だけ登録され、□から×に変わることを確認します。
6. HPの予約カレンダーでその日時が選べず、公開APIに顧客情報が出ていないことを再確認します。
7. 重なる別の予定がある枠は確定できず、同じ申込みの確定を再実行してもイベントが増えないことを確認します。
8. 重なる後続申込みへの案内停止、先行商談終了後の再判定、条件未了承時の停止、確認後の申込変更・予定追加による承認停止を確認します。
9. 検証用の宛先だけで自動案内を試す場合、両送信フラグを有効にして `runAutomaticGuidance` を実行します。確認済み請求額・了承済み条件の案件だけが対象となり、予約確定は行わないことを確認します。送信結果不明・送信失敗・準備済み案件を自動再送しないことも確認します。

メール受信、実Googleカレンダー権限、Preview画面、Vercel本番の受入確認はローカルテストでは代替できません。`ENABLE_CUSTOMER_SEND=true` は、テストがすべて完了し、本番運用の判断をした後に設定します。マージ・本番デプロイ・実顧客へのメール送信はこの作業では行いません。

## 自動案内のトリガー

動作確認後に、検証用回答スプレッドシートのフォーム送信時トリガーとして `onReservationFormSubmit` を設定できます。送信元シートが設定値と違うイベントは拒否します。公開のAPIから自動送信関数を起動する操作はありません。

後から管理者が確認内容を保存した案件を処理する場合は、同じプロジェクトの `runAutomaticGuidance` に時間主導型トリガーを設定します。頻度は運用時に決定し、このコードで自動設置しません。トリガー実行アカウントはinfo@送信・シート・予約カレンダーに必要な権限を持つ必要があります。

本番有効化前に既存の将来予約を照合してください。回答は残っていても確定履歴がない既存案件は□の対象になり得ます。既存カレンダー予定は競合として検出されますが、既存案件の状態移行を自動推測しません。
