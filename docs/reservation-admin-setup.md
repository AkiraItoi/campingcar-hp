# SUN AID 予約管理・振込案内の設定

## 構成と境界

- `/admin/` は管理UI。Vercelの `/api/admin` がGoogle署名付きIDトークンを検証して、1時間のHttpOnly / Secure / SameSite=Strictセッションを発行する。
- 許可アカウントは `sunaid20220708@gmail.com` と `info@izutrip.com`。info@でのログインはGoogle Workspaceの `hd=izutrip.com` も必要。Gmailでinfo@を開けるというだけではWorkspace本人アカウントと断定できない。エイリアスの場合は指定gmailアカウントを利用する。
- APIからHMAC署名したリクエストをGoogle Apps Scriptへ送る。Apps Scriptは署名・時刻・操作者を検証し、Script Lockで回答読取り・履歴更新・送信を排他制御する。
- 既存回答シートは読取りのみ。履歴は同じ非公開スプレッドシートの新しい `SUN_AID_送信履歴` タブへ保存する。
- トップページ・予約ページ・カレンダー・料金計算・既存フォーム導線・PDFは変更しない。フォーム送信トリガーは作らない。入金照合・予約確定処理も作らない。
- 新しいメール配信サービスや有料契約は不要。ただし既存Google / Vercelの権限・Apps Scriptの配信制限によって設定の調整が必要な場合がある。

## 1. フォームのメール収集

フォーム編集画面 → 設定 → 回答 → 「メールアドレスを収集する」を「回答者からの入力」へ変更する。
送信先を回答に保存するために必要。既存の日時・概算料金を渡す文章欄は変更しない。
フォーム設定後、回答シートの見出しに `メールアドレス` が追加されたことを確認する。別の見出しなら後述の `EMAIL_HEADER` に実際の見出しを設定する。
旧回答にメールアドレスがない場合は送信を止める。架空のアドレスや電話番号からの推定で補完しない。

## 2. Google Apps Script（送信できるinfo@アカウント側）

1. info@のGoogleアカウントで回答スプレッドシートを開き、拡張機能 → Apps Script。info@がエイリアスの場合は、info@を送信元エイリアスとして選べるアカウントで作成する。回答シートへの編集権限が必要。
2. `apps-script/Code.gs` の内容を `Code.gs` に入れる。
3. プロジェクト設定で「appsscript.json マニフェスト ファイルをエディタで表示する」を有効にし、`apps-script/appsscript.json` の内容を入れる。
4. プロジェクト設定 → スクリプト プロパティに以下を設定。実際の秘密値をGitHub、管理画面コード、チャットへ貼らない。

| 名前 | 値 |
|---|---|
| `SPREADSHEET_ID` | 指定された回答スプレッドシートURLの `/d/` と `/edit` の間のID |
| `RESPONSE_SHEET_ID` | 指定タブのgid（今回確認済み：`405558677`） |
| `EMAIL_HEADER` | `メールアドレス`（実際の列見出しに合わせる） |
| `BACKEND_SECRET` | 暗号学的乱数で生成した32文字以上。Vercel側と同じ値 |
| `ENABLE_CUSTOMER_SEND` | 初期値 `false`。テスト送信のみ可能 |

5. エディタで `setup` を1回実行し、権限を許可する。既存回答タブは変更せず、送信履歴タブだけ作成する。実メールは送信しない。送信元がinfo@にならない設定ではエラーで止まる。
6. デプロイ → 新しいデプロイ → ウェブアプリ。「次のユーザーとして実行」は自分。「アクセスできるユーザー」はGoogleログインを要求しない「全員」。ウェブアプリURLを控える。URLが公開でも、署名なしでデータ読取り・送信はできない。
7. Workspaceの管理ポリシーでこの公開方法が禁止されている場合は回避せず方式を再検討する。ウェブアプリURLを開いて `AUTH_REQUIRED` が返るのが正しい。

コードを更新した場合は既存デプロイを新しいバージョンへ更新する。「テストデプロイ」の `/dev` URLは使用しない。
GmailAppを使うためGmailアクセスとシート編集の認可が必要。スクリプトから外部へGoogleアクセストークンを渡さない。

## 3. Googleログイン用クライアント

既存Google Cloudプロジェクトにウェブアプリ用OAuthクライアントがあれば利用する。なければGoogleのログイン設定用に作成する。新しい有料サービスの契約は行わない。

1. OAuth同意画面 / Google Auth Platformを設定。指定gmailアカウントも使うため、Workspace内部限定にはしない。
2. OAuthクライアントの種類はウェブアプリケーション。
3. 承認済みJavaScript生成元へ管理ページのPreviewの **オリジン**（例：`https://実際のpreview-host`）を登録。パス `/admin/` は入れない。
4. テスト運用にGoogle側でテストユーザー登録が必要と表示される場合は指定の2アカウントを登録する。
5. クライアントIDを控える。クライアントシークレットは不要で、ブラウザにも入れない。

Previewと本番で同じクライアントIDを使う場合は両方の生成元を登録する。検証済みのGoogle署名・audience・issuer・有効期限・nonce・email_verifiedを確認する。画面上のメール文字列を信用して認証を通さない。

## 4. Vercel環境変数

対象プロジェクト → Settings → Environment Variablesで、まず今回のブランチのPreviewへ設定する。本番適用はレビュー・mainマージ後。

| 名前 | 値 | ブラウザに返すか |
|---|---|---|
| `ADMIN_GOOGLE_CLIENT_ID` | 前項のGoogleクライアントID | 公開識別子のみ返す |
| `ADMIN_ORIGIN` | 実際の管理画面URLのオリジン。末尾スラッシュ・パスなし | 返さない |
| `ADMIN_SESSION_SECRET` | 32文字以上の暗号学的乱数 | 返さない |
| `ADMIN_BACKEND_URL` | Apps Scriptの `/exec` URL | 返さない |
| `ADMIN_BACKEND_SECRET` | Apps Scriptの `BACKEND_SECRET` と同じ値 | 返さない |

2つの秘密値は別々に生成する。安全なローカル端末で `openssl rand -hex 32` 等を使い、出力を直接設定画面へ入力する。
環境変数変更後、該当ブランチをRedeployする。Previewには安定したブランチURLを使い、Googleの生成元と `ADMIN_ORIGIN` を一致させる。
未設定なら画面は「外部設定が必要です」と表示し、APIは顧客情報を返さない。

## 5. テスト・公開前確認

- 未ログインではAPIの回答読取り・メール送信が401になること。
- 指定外アカウントではアクセスできず、指定2アカウントでは利用できること。info@がエイリアスなら指定gmailで運用する。
- フォームへ架空の予約を入力し、宛先は自分のメールアドレスにする。実顧客への試験送信は禁止。
- 日時・メール・概算料金を一覧で確認する。不足・不正な項目は送信できないこと。
- 請求金額を変更し、本文に反映されること。金額変更後は以前の本文確認を無効にすること。
- 「テストメールを確認」で固定宛先 `sunaid20220708@gmail.com` と架空日時・100円を確認し、送信する。メールにはテストであり振込不要と記載する。
- 実際に受信し、送信元がinfo@・氏名・日時・金額・リンク・入金確認で確定・手数料負担が正しいことを確認する。Gmailが受付したという応答だけでは到達確認にならない。
- 送信履歴と時刻を確認し、連打・再読込みでも重複しないこと。振込案内を送っても「予約確定」にはならないこと。
- 確認後に `ENABLE_CUSTOMER_SEND=true` に変更すれば実顧客向けの送信ボタンが有効になる。この切替は実送信テストとレビュー完了後に行う。
- 初回テスト成功後は同じテストを再送しない。運用中の送信済み申込みも、このMVPでは再送できない。

## 状態と再送

| 状態 | 意味・操作 |
|---|---|
| 未対応 | まだ本文を作成していない |
| 送信前確認 | 宛先・本文・金額を履歴へ保存。15分で確認期限切れ。別の確認操作で旧プレビューを無効化 |
| 送信済み | Gmail送信呼出しが正常終了し、履歴保存済み。受信者への到達保証ではない |
| 未送信・再確認可 | Gmail呼出し前に送信元設定で停止、または管理者が未送信を確認。新しいプレビューで再試行できる |
| 結果不明 | Gmailエラー、送信後保存失敗、継続中の送信。自動再送は禁止 |

処理開始から5分以上待ち、info@の送信済みフォルダで宛先・本文・日時を確認する。まだ処理中ならScript Lockが手動変更を拒否する。
確認できた場合だけ「送信を確認した」または「未送信を確認した」で解決する。判断できなければ結果不明を維持する。
手動で送信を確認した場合、実送信時刻を捏造せず、確認日時と確認者を別に保存する。
履歴タブの削除・並べ替え・直接書き換えや、元の回答タイムスタンプの変更は行わない。タイムスタンプ衝突は両回答を停止し、個別確認とする。
2000行を超える回答または5000行を超える履歴では処理を停止する。容量拡張が必要になった時点でページング・保存先を検討する。
送信済みの正式な再送、銀行入金照合、予約確定操作は今回の範囲外。

## ローカル検証

`npm ci` → `npm test`。
Node APIはテスト時にGoogle検証結果をモックし、Apps Scriptはシート・Gmail・Lockのモックで障害を再現する。実Google認証・実配信・実Vercel・画面表示の受入検証とは別。実運用完了とは扱わない。
